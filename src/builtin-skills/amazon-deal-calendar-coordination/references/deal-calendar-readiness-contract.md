# 活动日历协调方法

## 1. 每个活动的最小事实

确认活动名称、站点、商品范围、来源、计划窗口、时区、负责人和决策日期。只有名称时可以登记 `TBD`，不能给出可执行日期。

## 2. 时间处理

分别记录报名截止、素材截止、价格生效、活动开始/结束、库存准备和复盘窗口。所有时间保留时区；只有来源明确时才换算。

窗口冲突时显示原始时间和冲突影响，不自行移动日期。

## 3. 依赖门

至少核对：

- 活动规则、资格和费用是否有带日期依据；
- 价格与叠加方案是否通过专家 06 自身价格门；
- 增量经济是否通过，或明确仍待专家 14 输入；
- 库存/补货责任方是否确认；
- 素材、文案、合规和批准是否齐全；
- 谁负责报名、提交和结果回填。

所有必需依赖通过才可建议推进。有明确条件、负责人和截止日期时可写“条件满足后推进”；硬门失败则停止。`TBD` 不会自动转为默认日期。

## 4. 三 MCP 边界

SIF、SellerSprite 和 Sorftime 都不能证明 Amazon 活动规则、窗口、资格、活动费、批准、报名、库存或平台状态，因此本 Skill 不直接调用它们。其他 Skill 的市场观察只能作为对象背景，不能提升日历就绪程度。

## 5. 冲突与变更

保留每次窗口、规则或负责人变化的来源和日期。新信息不覆盖旧记录；说明哪些活动、依赖和决策受到影响。

## 6. 交付

日历应展示活动、窗口、依赖、当前判断、阻塞、责任人和下一行动。用户要求提醒或自动报名时，只给可导入的静态计划，由有权限系统另行执行。
