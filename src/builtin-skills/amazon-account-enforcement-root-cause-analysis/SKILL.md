# Amazon 账号执法事件根因分析

## 什么时候使用

使用本 Skill：

- 同一账号或多个 ASIN 出现重复、关联或升级的通知与限制；
- 用户需要解释事件背后的流程、质量、供应商、权限或变更控制失效；
- 已有多个单案材料，需要形成账号级纠正与预防方案；
- POA 写作前，需要先得到可追溯、可复核的根因。

不要使用本 Skill：

- 只需回复一个买家消息、退货、A-to-z 或拒付案件，交第11专家；
- 需要判断某项政策或知识产权实体是否成立，交第09专家；
- 只有公开评论或市场数据、没有账号通知；
- 用户要求直接提交申诉、持续监控或保证恢复。

## 完成标准

合格结果应让审核者看清：

1. 发生了哪些事件，先后关系和影响范围是什么；
2. Amazon 明示的问题与内部观察到的事实分别是什么；
3. 哪些事件可能共享同一个控制失效；
4. 每条“事件—直接原因—控制失效—根因”的连接由什么材料支撑；
5. 哪些替代解释仍未排除；
6. 应立即止损、纠正什么，以及如何防止复发；
7. 哪些缺口会阻止进入 POA。

根因分析完成不等于 Amazon 已接受，也不等于账号一定恢复。

## 输入与边界

优先使用：

- 账号或 ASIN 级通知原文、后台截图、案件回执和截止日期；
- Listing、产品、质检、供应商、履约、客服、权限和变更记录；
- 第09专家带适用范围和限制的政策/IP判断；
- 第11专家交接的多个版本化单案事实；
- 第13专家提供且能追溯到单案集合、期间和计算口径的聚合信号；
- 已采取行动的执行记录与效果证据。

至少要有一份可定位的执法或限制材料。只有用户转述时，可先整理待核问题，但不得宣布根因成立。

公开产品评论只能提示“可能存在的体验主题”，不能证明账号投诉、订单关系、执法原因或发生率。`sif_mcp`、`sellersprite_mcp`、`sorftime_mcp` 的公开市场数据均不具账号后台语义，本 Skill 不调用它们。

`uploads/` 保持只读；过程材料放入 `temp/account-risk/<case-id>/02-enforcement-rca/`，正式结果写入 `outputs/account-risk/<case-id>/02-enforcement-rca/`。账号、买家、证件、银行和税务信息应掩码。

## 执行流程

### 1. 先确认问题和范围

向用户确认账号、站点、涉及对象、希望解释的事件范围和当前最紧迫的截止时间。若材料跨站点、跨账号或跨法人，先拆分再分析。

说明当前能做的是：

- 重建事件与行动；
- 提出并验证根因候选；
- 形成整改候选和 POA 交接。

不能做的是替 Amazon 解释内部决策，或用缺失数据推断“没有其他事件”。

### 2. 建立事件账本

每个事件至少写清：

- 发生了什么、影响哪个账号/站点/ASIN；
- 通知日、截止日和当前状态；
- Amazon 原文中的问题、要求和政策指向；
- 事件前后的产品、Listing、流程、供应商或权限变化；
- 用户已采取的行动及其证据；
- 当前仍不确定的事实。

公共 Review 不创建执法事件。未知日期明确写“待确认”，不要用叙事顺序冒充时间。

### 3. 重建时间线

把通知、投诉、流程变更、供应商批次、质检异常、Listing 修改、权限操作和处置回执按时间排列。重点寻找：

- 同一变更之后是否出现多起相似事件；
- 事件是否集中于同一产品、供应商、站点或操作角色；
- 止损后新事件是否仍发生；
- Amazon 后续是否验证或否定了某个解释。

时间上先发生只说明“可能相关”，不能单独证明因果。

### 4. 编码模式，但不急于下结论

可按以下业务维度聚类：

- 商品实物与 Listing 承诺不一致；
- 质量、安全或合规控制失效；
- 供应商文件、批次或追溯失效；
- 权限、审批、发布或变更控制失效；
- 履约、客服或订单流程的重复性缺陷；
- 政策/IP适用问题；
- 材料不完整造成的证据盲区。

模式用于聚合同类事实，不等同于根因。一个高频标签也可能只是表象。

### 5. 构建并检验因果链

对每个候选根因依次回答：

1. 观察到的事件是什么？
2. 最接近事件的直接原因是什么？
3. 哪个控制本应预防或发现它？
4. 该控制为何没有发挥作用？
5. 哪个流程、职责、供应商或治理问题造成控制持续失效？
6. 有哪些材料支持每一步？
7. 哪些替代解释也能解释这些事实？
8. 要补什么证据才能区分它们？

每条连接按自然语言标明“已直接支持”“有部分支持”或“尚未验证”。不要使用任意权重或打分掩盖证据缺口。

### 6. 决定能否确认根因

只有在以下条件同时成立时，才把候选提升为可供整改与 POA 使用的根因：

- 至少一条完整因果链有直接材料支撑；
- 关键时间关系一致；
- 主要替代解释已被证据排除或明确受限；
- 根因能解释多个事件或解释为何控制未能阻止单个重大事件；
- 拟议动作直接针对该控制失效，而非只重述问题。

否则输出“根因候选”，列出验证计划，不生成已确认根因。

### 7. 设计纠正与预防措施

严格区分：

- **立即遏制**：停止继续产生风险；
- **即时纠正**：修复已发生的问题；
- **纠正措施**：消除已确认根因；
- **预防控制**：防止同类问题在其他对象复发；
- **有效性验证**：用什么观察证明措施真实有效。

每项措施写负责人、截止时间、影响对象、所需执行证据和验证时点。建议、计划、执行中和已验证完成不能混写。

### 8. 复核跨专家交接

- 第09输出只用于政策/IP实体判断，不由本 Skill 改写；
- 第11单案事实必须能定位到对应版本，本 Skill只做跨案共因；
- 第13聚合只有在单案集合、期间、分母、遗漏和算法可解释时才作为模式证据；
- 本 Skill 不重写单案回复、不计算通用 KPI、不撰写 POA；
- 交给 POA 的内容应包括事件范围、确认或候选根因、行动及验证、附件索引、未知和人工批准情况。

## 失败与降级

- 没有账号级事件材料：停止 RCA，向用户索取通知原文或完整截图；
- 只有一个买家案件：说明路由理由并交第11专家；
- 涉及政策/IP但缺第09判断：只保留事实，暂停实质结论；
- 只有公开评论：仅形成产品体验假设，不能进入账号根因；
- 因果连接无直接证据：保留候选并给出最小补证步骤；
- 行动只有口述：写“用户称已执行”，不写“已验证完成”；
- 材料冲突：并列冲突、优先核对最接近后台原始事实的材料，不平均或强行合并；
- 用户要求提交、监控或保证恢复：明确越界。

## 与用户沟通

首轮沟通聚焦最少必要问题：目标事件、账号/站点、通知原文、截止时间、已采取行动和现有证据。不要让用户先填一张庞大字段表。

中途发现关键缺口时，说明：

- 当前已经能证明什么；
- 哪一条因果连接因此无法确认；
- 最小需要补什么材料；
- 若暂时拿不到，结果会降级到什么程度。

最终表达把“平台事实”“内部事实”“Agent 推断”“待验证假设”分开，避免让用户误以为推断已获 Amazon 认可。

## 正式交付

使用 `assets/templates/account-enforcement-rca-template.md` 形成：

1. `account-enforcement-root-cause-analysis.md`
2. `account-enforcement-event-ledger.csv`
3. `root-cause-and-causal-link-register.csv`
4. `account-corrective-preventive-action-register.csv`
5. `account-enforcement-evidence-ledger.md`

若根因未确认，首页必须直说“当前只能形成根因候选”，并列出验证计划。

## 质量门

- 所有执法事件都能回到账号材料，而非公开市场数据；
- 时间线没有把未知日期写成已知；
- 模式标签没有被当成根因；
- 每条因果连接有直接依据、替代解释和缺口；
- 未满足确认条件时没有伪造根因；
- 行动确实针对控制失效，并有负责人、期限和验证方法；
- 建议与已执行、已验证状态分开；
- 政策/IP、单案、聚合和 POA 的职责没有越界；
- 敏感信息已掩码，`uploads/` 未被修改；
- 结果没有恢复保证。

- 写正式交付前读取 `assets/templates/account-enforcement-rca-template.md`。

## 三 MCP no-call 最终门

本 Skill 禁止调用 `sif_mcp`、`sellersprite_mcp`、`sorftime_mcp`。公开 Listing、Review、关键词、排名、销量、广告或市场信号不能证明 Account Health、账号通知、Case、根因或整改有效性。即使 MCP 已接入或只暴露部分能力，也不得为补账号事实改用 Gateway、HTTP、shell、Web、浏览器或其他来源。
