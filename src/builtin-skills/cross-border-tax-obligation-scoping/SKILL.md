# 跨境税务义务范围界定

## 目标与完成定义

本 Skill 回答“需要向税务专业人员确认什么”，而不是自行报税：

1. 哪些法定实体参与了采购、进口、库存、销售、收款和退款；
2. 货物、订单、所有权、发票和资金如何流动；
3. 哪些国家/地区、日期和业务事件可能触发税务问题；
4. 用户提供的现行依据或专业意见覆盖什么；
5. 注册、税号、申报、发票、平台代征或记录义务还缺什么证据；
6. 由谁在什么时间点做出合格判断。

最高完成状态是 `ready_for_qualified_tax_review`，不是“无需注册”或“税务已合规”。

## 运行合同

### 合法输入

- 用户对话及只读 `uploads/` 中的主体资料、业务模式、合同、发票、平台结算、库存地点、物流、付款、退款和既有税务登记；
- 用户或可信上游提供的带日期法规/官方说明/专业意见；
- 可信 `outputs/` 中的商品、海关、运营、利润和市场信息；
- 合格税务顾问、会计师或法务人员的可追溯结论。

当前税率、门槛、申报周期、平台代征和注册义务只能来自用户或可信上游带日期依据。Agent 不从记忆补充。

### 外部数据边界

- 不调用 `sif_mcp`；当前 SIF 目录没有税务、税率、注册或申报能力，商品/销量估算也不能证明税务义务或应税额；
- 运行时输入仅限用户对话、只读 `uploads/` 与带来源/日期/版本的可信 `outputs/`；
- 不使用 Web、税务网站、VAT 计算器、汇率 API、DeepL、其他 MCP/API；
- 不读取税务平台密钥或登录信息；
- 不注册税号、不生成可提交申报、不付款；
- 现行依据不足时只形成事实包和咨询问题。

### 工作区

- `uploads/` 只读；
- `temp/compliance/<case-id>/02-tax-scoping/` 存放实体、货物/订单/资金流、事件和义务候选草稿；
- `outputs/compliance/<case-id>/02-tax-scoping/` 存放唯一正式范围包；
- 身份、税号、银行和客户信息在输出中最小化和掩码。

### 双层谱系

输入证据保留 `evidence_id`、`source_path`、主体、司法辖区、事件日期、期间、币种、四轴和敏感性。

Agent 的实体关系、事件编码、义务候选、缺口和专业问题为 `agent_output`，记录 `parent_evidence_ids`、转换类型、假设状态和结论上限。

四轴：

- `source_type`
- `temporal_scope`
- `estimation_status`
- `transformation_type`

## 启动检查

### 最低输入

至少需要：

1. 参与业务的法定实体及角色；
2. 销售市场和期间；
3. 商品从哪里到哪里、在哪里库存；
4. 谁与客户交易、开票、收款和退款；
5. 平台、渠道和客户类型；
6. 现有登记、申报或专业意见；
7. 用户希望确认的决策和合格责任方。

### 状态

- `ready_for_qualified_tax_review`
- `facts_partial`
- `entity_or_flow_conflict`
- `current_authority_missing`
- `registration_evidence_missing`
- `period_or_currency_conflict`
- `blocked`
- `out_of_scope`

### 来源缺失语义（与业务状态分列）

业务 `result_status` 继续使用上述税务范围状态；每个实体、业务流、交易或依据字段另记 `source_availability_status`，只允许 `not_returned / not_queried / parse_failed / missing / conflicted / true_zero`。只有完整、可验证覆盖明确证明的零可以使用 `true_zero`。

前五项不得写成 0、无交易、无税务义务或无风险，也不得替代 `current_authority_missing/registration_evidence_missing/...` 等业务门禁。正例：完整期间交易导出明确显示退款笔数为 0，可记 `true_zero`，义务候选仍由现行依据和责任方确认。反例：平台代征字段未返回时记 `not_returned`，不能写“平台代征为 0”或“无需申报”。

## 执行流程

### 第一步：建立实体与角色图

分别记录：

- 法定实体、注册地和税务识别信息（输出掩码）；
- 卖方、进口商、库存所有人、平台店铺主体、收款人、退款责任方；
- 关联企业和服务商；
- 合同/发票/平台账户与法定实体的证据；
- 身份冲突。

名称相同或关联关系不等于同一纳税主体。

### 第二步：建立货物、订单、发票与资金流

对每种业务模式记录：

- 采购与所有权转移；
- 进口、清关和库存地点；
- 订单接收、卖方和客户类型；
- 发票/收据开具；
- 平台代收、代征或结算陈述；
- 退款、退货和折让；
- 收款币种、账户和汇兑；
- 相关期间和证据。

平台结算扣款不自动等于税款已申报。

### 第三步：固定司法辖区和事件

每个事件记录：

- `tax_event_id`
- 国家/地区及子辖区；
- 事件类型；
- 发生日期；
- 商品、订单、库存和主体范围；
- 金额/数量仅作为输入事实；
- 来源证据；
- 当前依据需求。

不同辖区和期间不得合并。

### 第四步：登记现行税务依据

记录：

- 标题、发布主体和来源路径；
- 发布、生效、修订和提供日期；
- 适用主体、交易和地区；
- 原文/摘要/翻译/专业意见状态；
- 阈值、税率或日期是否由责任方确认；
- 限制。

没有带日期原文或专业输出时，不得宣布现行义务。

### 第五步：形成义务候选

义务候选可以包括需要确认的：

- 注册或税号；
- 申报或报表；
- 发票/记录；
- 平台代征与卖家剩余责任；
- 进口税务角色；
- 退货、退款和折让处理；
- 关联实体/服务；
- 数据保留；
- 专业复核。

每项都必须写成问题或候选，不写确定结论。

### 第六步：映射现有资料

检查：

- 登记主体、号码、辖区和有效日期；
- 申报期间和提交证据；
- 平台报表的税务字段与定义；
- 发票、订单、退款和结算；
- 专业意见的适用事实和有效期；
- 业务变化是否超出原结论范围。

“曾经注册/申报”不等于当前模式已经覆盖。

### 第七步：处理阈值和税率

仅当用户或可信上游提供带日期依据时：

- 原样记录阈值/税率及适用条件；
- 标明币种、期间、计算基础和责任方；
- 不自行把销售估算套入；
- 不换算或计算应纳税额；
- 不把临近阈值写成必然触发。

无依据时字段为 `qualified_confirmation_required`。

### 第八步：建立专业咨询问题

每个问题包含：

- 完整业务事实；
- 司法辖区和日期；
- 相关依据；
- 现有登记/报表；
- 问题的封闭形式；
- 需要的结论和证据；
- 责任方、截止时间和业务闸门。

### 第九步：形成行动清单

允许行动：

- 补业务事实；
- 获取现行原文；
- 请求税务顾问确认；
- 核对登记/申报证据；
- 准备数据字段和记录保留；
- 暂停未经确认的业务决策。

不允许：

- 自动注册、申报、付款；
- 生成可提交税表；
- 宣称税务意见已经出具。

## 失败与降级

- `entity_unknown`：不判断义务；
- `goods_or_money_flow_missing`：仅交付事实缺口；
- `current_authority_missing`：不提供税率/阈值；
- `conflicting_professional_opinions`：并列范围和日期，要求责任方解决；
- `sensitive_data_exposure`：掩码并最小化；
- `calculation_requested`：转交合格税务/第14经济分析，但不计算税款；
- `out_of_scope`：税务意见、注册、申报、付款、稽查应对或保证合规。

## 正式交付

至少生成：

1. `tax-obligation-scoping.md`
2. `entity-goods-order-money-flow-register.md`
3. `tax-event-and-obligation-candidate-register.csv`
4. `qualified-tax-question-pack.md`
5. `tax-evidence-ledger.md`

使用 `assets/templates/tax-obligation-scoping-template.md`。首页明确“范围界定，非税务意见或申报结果”。

## 质量门

- 法定实体和角色分开；
- 货物、订单、发票和资金流可追溯；
- 司法辖区、事件和期间明确；
- 现行税务事实只来自带日期依据；
- 阈值、税率和平台代征没有由 Agent 猜测；
- 义务保持候选/问题状态；
- 既有登记与当前业务模式逐项匹配；
- 敏感身份和税务信息已最小化；
- 无计算、注册、申报、付款或外部网站；
- 双层谱系与工作区合同完整。
