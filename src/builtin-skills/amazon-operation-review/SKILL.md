# Amazon 运营复盘归因分析技能

将卖家精灵趋势图 + listing变动历史转化为可归因的复盘报告，回答"什么操作改变了我的数据，效果是好是坏"。

核心原则：一个拐点只有当合理的运营事件落在可信的因果时间窗口内、且指标变化方向与操作类型一致时，才具有归因意义。相关性不等于因果性。

## When to Invoke / 触发条件

当用户表达以下任一意图时触发：
- "帮我复盘一下这个ASIN最近的运营效果"
- "为什么我6月订单突然掉了？/ BSR突然跳变？"
- "归因分析：价格/标题/主图改动对销量的影响"
- "卖家精灵的拐点和我做的运营操作对不上号，帮我梳理"
- "把这段时间的listing变动和趋势图做成一份复盘报告"
- "Did my title rewrite help? Was the Lightning Deal worth it?"
- 用户上传了卖家精灵/Keepa等工具的趋势图截图或数据导出文件
- 用户上传了listing变动监控截图
- 用户仅提供ASIN编号要求复盘（自动触发 `amazon-monitoring-data-fetch` 获取数据）

## Skill Linkage / 技能联动

本技能与 `amazon-monitoring-data-fetch` 技能双向联动：

**正向联动（data-fetch → operation-review）：** 当 data-fetch 检测到用户意图为"操作分析/还原竞品操作/复刻操作/还原动作"时，获取数据后自动链入本技能。本技能读取 data-fetch 输出的标准化CSV（Format 4）作为输入。

**反向联动（operation-review → data-fetch）：** 当用户仅提供ASIN编号但未提供趋势数据或变动记录时，本技能自动回退到 data-fetch 获取所需数据，获取完成后继续分析。

详细数据契约和交接协议：`amazon-monitoring-data-fetch` 技能的 `references/skill-linkage.md`。

## Input Requirements / 输入要求

支持四种输入格式（至少提供趋势数据 + 变动记录各一项）：

### 格式1：截图（最常见）
- **趋势图截图**：价格趋势、订单量趋势、BSR排名、评分趋势、评论分析
- **变动监控截图**：标题变更、主图变更、Bullet Point变更、价格变更
- 每张图需包含：ASIN、日期范围、Y轴刻度、趋势线

### 格式2：CSV/XLSX数据导出
- 卖家精灵导出的Excel/CSV，包含上述趋势数据和变动监控sheet
- 需统一时区为UTC+8，统一日期格式为YYYY-MM-DD

### 格式3：自由文本运营日志
- 用户手动记录的运营动作（日期+操作内容）
- 需解析为结构化事件：日期、变更类型、变更内容

### 格式4：data-fetch 技能输出（自动衔接）
- 当 `amazon-monitoring-data-fetch` 技能完成数据获取后，其输出的标准化CSV直接作为本技能输入
- 读取工作目录 `<workspace>/asin_monitor_<YYYYMMDD_HHMM>/` 下的CSV文件
- **数据文件映射：**

| data-fetch 输出文件 | 本技能Stage 0数据类型 | 兼容性 |
|-------------------|-------------------|-------|
| `price.csv` | 价格数据 | 字段直接映射 |
| `orders.csv` | 订单数据 | 字段直接映射 |
| `bsr.csv` | BSR数据 | 字段直接映射 |
| `rating.csv` | 评分数据 | 字段直接映射 |
| `listing_changes.csv` | 变动记录 | 需补充severity和expected_sign |
| `reviews.csv` | 评论分析（附加） | 供因果验证使用 |
| `review_keywords.csv` | 评论主题（附加） | 供第三轴验证使用 |
| `manifest.json` | 元数据 | 获取数据来源、配额状态、缺失信息 |

- **字段补充：** `listing_changes.csv` 中的 `change_type` 和 `change_subtype` 可直接映射，但 `severity` 和 `expected_sign` 需由本技能 Stage 0 根据事件分类体系自动补充
- **缺失数据处理：** 若 manifest.json 显示某些数据缺失，按降级策略继续分析（见 Stage 0 降级规则）

## Analysis Workflow / 分析流程（七阶段）

### Stage 0: Data Ingest & Normalize (数据接入与标准化)

将不同格式的输入统一为标准化数据结构：

**趋势数据标准化为4类：**
| 数据类型 | 必需字段 | 可选字段 |
|---------|---------|---------|
| 价格数据 | date, amazon_price | new_offer_price, listing_price, discount_price, member_price, subscribe_price |
| 订单数据 | date, order_volume | estimated_sales |
| BSR数据 | date, main_category_rank | sub_category_rank_1, sub_category_rank_2 |
| 评分数据 | date, star_rating | review_count, new_reviews_today |

**变动记录标准化为：**
| 字段 | 说明 | 取值示例 |
|------|------|---------|
| date | 变更日期 | 2026-07-29 |
| change_type | 变更大类 | title / bullet / main_image / a_plus / video / price / coupon / deal / vine / ppc / inventory / merge_split / other |
| change_subtype | 变更子类 | keyword_expand / keyword_replace / first_image_swap / sub_image_swap / price_drop / price_hike |
| severity | 严重程度 | minor / moderate / critical |
| detail | 变更详情 | "追加关键词: Air Planter, Gardening Gifts" |
| expected_sign | 预期影响方向 | + (正面) / − (负面) / ? (不确定) |

**严重程度判定标准：**
| 等级 | 标准 | 示例 |
|------|------|------|
| minor | 单词调整、单张副图替换、图片顺序调整 | 第3张副图替换 |
| moderate | Bullet Point重写、副标题变更、多张图替换 | 第3-7张图替换 |
| critical | 整体标题重写、类目节点变更、父变体合并/拆分、Lightning Deal、断货恢复 | 标题追加10+关键词 |

**Format 4 (data-fetch CSV) 读取规则：**

当输入为 data-fetch 技能输出的CSV工作目录时：

1. 读取 `manifest.json` 获取元数据（ASIN列表、角色、时间范围、数据来源、缺失信息）
2. 按 `references/skill-linkage.md` 的数据契约映射，将CSV字段直接映射为标准化数据结构
3. 对 `listing_changes.csv`，根据 `change_type` 和 `change_subtype` 自动补充 `severity` 和 `expected_sign`：
   - severity 判定：参考上表"严重程度判定标准"
   - expected_sign 判定：参考 Stage 2 事件分类体系的 expected_sign 列
4. 利用 `reviews.csv` 和 `review_keywords.csv` 作为附加验证数据（第三轴验证）

**数据缺失降级规则（Format 4 专用）：**

| 缺失数据 | 降级策略 |
|---------|---------|
| `price.csv` 缺失 | 跳过价格拐点识别，其他分析正常 |
| `orders.csv` 缺失 | 无法进行订单量拐点识别，标注"订单数据不可用" |
| `bsr.csv` 缺失 | 跳过BSR拐点识别 |
| `rating.csv` 缺失 | 跳过评分拐点识别 |
| `reviews.csv` 缺失 | 跳过评论主题分析，因果验证缺少第三轴 |
| `listing_changes.csv` 缺失 | **无法进行归因分析**（核心输入），仅输出趋势分析 |
| `manifest.json` 显示配额耗尽 | 在报告中标注"部分数据因MCP配额不足而缺失，结论可能受影响" |

### Stage 1: Inflection Point Detection (拐点识别)

对每类趋势数据执行指标特定的拐点识别。

**通用识别规则：**
| 拐点类型 | 识别标准 | 示例 |
|---------|---------|------|
| 上升拐点 | 指标从平稳/下降转为显著上升 | 订单量从4000跳升至8000 |
| 下降拐点 | 指标从平稳/上升转为显著下降 | BSR大类排名从500恶化至2500 |
| 波动拐点 | 剧烈波动后趋势方向改变 | 价格从$19骤降至$13后持续低位 |
| 平台拐点 | 指标在新的水平线上稳定（与之前平台差异≥10%） | 订单量从4000平台切换至5000平台 |

**指标特定规则：**

| 指标 | 特殊规则 | 基线计算方法 |
|------|---------|------------|
| 价格 | 24h内变动>5%即为拐点；区分"促销波动"与"调价拐点"（新价格持续>3天=调价） | 前7日均价 |
| 订单量 | 单日变动>30%（相对滚动7日基线）即为拐点 | 滚动7日均值 |
| BSR排名 | **穿越整数阈值**（100/500/1k/5k/10k/20k）即为拐点；注意排名数值下降=变好 | 前14日中位数 |
| 评分 | 单日评论数突增≥3倍（相对前14日均值）；星级变动≥0.1 | 前14日均值 |
| 评论数 | 突增≥3倍=可能的Vine/测评/差评事件 | 前14日日均 |

**关键：基线比较法**
所有拐点判断必须使用基线比较，而非简单的日环比：
- 变更后7日均值 vs 变更前14日均值
- 只有两者差异超过阈值才认定为拐点
- 避免单日噪声导致的误判

**BSR方向提醒：** 排名数值下降=变好，排名数值上升=变差。分析时务必注意Y轴方向。

### Stage 2: Event Extraction & Classification (事件提取与分类)

从变动记录中提取所有运营事件并分类。

**完整事件分类体系：**

| 变更类型 | 子类型 | severity | expected_sign | 示例 |
|---------|-------|----------|--------------|------|
| title | keyword_expand | moderate | + | 在原标题后追加新关键词 |
| title | keyword_replace | moderate | ? | 删除旧关键词替换为新关键词 |
| title | full_rewrite | critical | ? | 整体标题结构改变 |
| main_image | first_image_swap | critical | ? | 第1张图更换 |
| main_image | sub_image_swap | minor-moderate | + | 第2-7张图更换（视数量） |
| main_image | image_reorder | minor | ? | 图片位置互换 |
| main_image | image_add_remove | minor | ? | 图片数量变化 |
| bullet | rewrite | moderate | + | 五点描述修改 |
| a_plus | content_change | moderate | + | A+页面内容修改 |
| video | add_remove | moderate | + | 视频新增或删除 |
| price | price_drop | moderate-critical | + | 价格下调 |
| price | price_hike | moderate-critical | − | 价格上调 |
| price | coupon_set | minor-moderate | + | 设置Coupon |
| deal | lightning_deal | critical | +(临时) | Lightning Deal |
| deal | best_deal | critical | +(持续) | Best Deal/7-Day Deal |
| vine | launch | moderate | +(延迟) | Vine计划启动 |
| ppc | budget_change | moderate | ? | PPC预算/竞价调整 |
| inventory | stockout | critical | − | 断货 |
| inventory | restock | moderate | + | 补货恢复 |
| merge_split | variation_change | critical | ? | 变体合并/拆分 |

### Stage 3: Time Correlation Matching (时间关联匹配)

将Stage 1识别的拐点与Stage 2提取的事件按时间窗口匹配。

**时间窗口规则（关键）：**

| 变更类型 | 影响开始 | 影响峰值 | 影响衰减 | 匹配窗口 |
|---------|---------|---------|---------|---------|
| 价格变更 | T+0~1天 | T+1~3天 | T+7~14天 | [T−1, T+14] |
| 促销活动(LD/BD) | 活动期间 | 活动期间 | 活动后3~7天 | [活动开始, 活动结束+7天] |
| 主图变更 | T+0~3天 | T+3~7天 | T+14~30天 | [T−1, T+30] |
| 标题变更 | T+2~7天 | T+7~14天 | T+14~30天 | [T−3, T+30] |
| Bullet Point变更 | T+3~7天 | T+7~14天 | T+14~30天 | [T−3, T+30] |
| A+/视频变更 | T+3~7天 | T+7~14天 | T+14~30天 | [T−3, T+30] |
| Vine/评论变化 | T+1~7天 | T+7~14天 | T+30~60天 | [T−1, T+30] |
| PPC调整 | T+0~1天 | T+1~3天 | T+7~14天 | [T−1, T+14] |

**匹配逻辑：**
1. 对每个拐点，检查其日期是否落在任何事件的匹配窗口内
2. 对每个事件，检查其窗口内是否出现拐点
3. 记录所有匹配对（拐点, 事件, 时间差）
4. 未匹配的拐点标记为"未归因"（可能为外部因素）
5. 未匹配的事件标记为"无显著影响"

### Stage 4: Causal Analysis (因果归因)

对每个匹配对进行**三轴评分**，判断因果关系。

#### 4.1 三轴评分体系

| 评分轴 | 检查内容 | 权重 | 通过标准 |
|-------|---------|------|---------|
| **时间匹配** | 事件是否在拐点的合理因果窗口内 | 30% | 时间差落在匹配窗口内 |
| **方向匹配** | 拐点方向是否与expected_sign一致 | 40% | 实际方向=预期方向 |
| **幅度匹配** | 变化幅度是否与操作severity相称 | 30% | minor操作不引起critical级变化 |

**幅度匹配的关键原则：**
- 单张副图替换(minor) 不应导致 订单量60%暴增 → 幅度不匹配
- Lightning Deal(critical) 导致订单量100%暴增 → 幅度匹配
- 标题关键词追加(moderate) 导致BSR从#500跳至#50 → 幅度可能过大，需检查混淆因素
- 一个minor操作匹配到一个critical级拐点时，置信度必须降级

#### 4.2 因果置信度评估

| 置信等级 | 标准 | 说明 |
|---------|------|------|
| **高置信** | 三轴全部通过 + 无混淆因素 | 强因果推断 |
| **中置信** | 时间+方向通过，幅度部分匹配，或存在轻微混淆因素 | 可能因果 |
| **低置信** | 时间通过但方向不符，或幅度严重不匹配，或多事件竞争 | 因果不确定 |
| **未归因** | 无事件落在窗口内，或逻辑上无法解释 | 排除因果关系 |

**混淆因素降级规则：**
当窗口内存在混淆因素（见Stage 4.3），**置信度自动降一级**：
- 高→中，中→低，低→未归因

#### 4.3 混淆因素排查（每次归因必查）

**必须检查的混淆因素清单：**
- [ ] **平台大促**：Prime Day、黑五网一、Prime Big Deal Days
- [ ] **节日季节性**：母亲节、父亲节、圣诞节等（影响礼品类目）
- [ ] **类目季节性**：如园艺类5-7月旺季、取暖类10-1月旺季
- [ ] **竞品操作**：主要竞品是否同时降价/促销/加大广告
- [ ] **Buy Box丢失**：是否失去购物车
- [ ] **断货**：产品是否断货（FBA库存耗尽）
- [ ] **Listing被抑制**：是否被亚马逊下架/暂停
- [ ] **PPC变化**：广告预算/竞价是否有调整
- [ ] **Coupon到期**：优惠券是否到期或新设
- [ ] **变体变更**：是否有变体增减/拆分
- [ ] **类目节点变更**：是否更换了类目节点
- [ ] **算法更新**：亚马逊是否进行了算法/政策调整
- [ ] **多事件叠加**：同一时间窗口内是否有多个运营操作同时发生

#### 4.4 多事件竞争处理

当同一窗口内有多个事件可能解释同一拐点时：
- **报告所有候选事件**，不强行选出一个"赢家"
- 置信度标记为`低`，注明"多事件竞争"
- 按severity从高到低排序候选事件
- 建议用户在未来将运营操作间隔至少7天以便区分

### Stage 5: Impact Assessment (影响评估)

对每个确认因果关系的匹配对，评估影响的性质和程度。

**评估维度：**

| 维度 | 说明 | 取值 |
|------|------|------|
| 影响方向 | 对业务是好是坏 | 正向 / 负向 / 中性 |
| 影响程度 | 变化幅度的大小 | 显著(>30%) / 中等(10-30%) / 轻微(<10%) |
| 持续性 | 效果是否持续 | 持续(>30天) / 临时(<14天) / 未知 |
| 可复制性 | 是否可再次操作获得同样效果 | 高 / 中 / 低 |
| ROI评估 | 操作成本与收益的关系 | 正收益 / 负收益 / 不确定 |

**趋势方向判断规则：**
- 订单量↑ + BSR排名变好(数值↓) = **正向**
- 订单量↓ + BSR排名变差(数值↑) = **负向**
- 价格↓ + 订单量↑ + BSR排名变好 = **正向但需关注利润率**
- 评分↓ + 订单量↓ = **负向，需紧急处理**
- 促销期间订单量↑ + 促销后订单量↓回基线 = **中性（临时正面，无持续效果）**
- 评分↑但订单量无变化 = **中性（社会证明增强但未转化为销量）**

**基线比较法（必须使用）：**
- 比较变更后7日均值 vs 变更前14日均值
- 不使用单日环比，避免噪声误判
- 标注比较窗口和均值数值

### Stage 6: Report Generation (报告生成)

根据用户请求类型，输出不同格式的报告。

#### 输出契约

**场景A：完整复盘报告**（用户要求"复盘""归因分析""做报告"）

输出结构化Markdown报告：

## Causal Honesty Rules / 因果诚实规则

1. **相关性≠因果性**：时间匹配只是必要条件，不是充分条件。
2. **不臆造原因**：如果拐点没有附近的运营事件，原因是外部因素。标注"未归因/外部因素可能性高"并给出假设，不强行归因。
3. **多事件不强行二选一**：当多个事件竞争时，报告所有候选并标注低置信度。
4. **使用审慎语言**：用"最可能的解释是…""不能排除…的影响"而非"这是因为…"。
5. **标注数据局限**：截图中的数据为估算值（如卖家精灵的订单量估算），分析结论应注明数据来源的局限性。
6. **观察期不足时明确说明**：标题/Bullet Point变更后不足14天的分析结论应标注"观察期不足，结论待验证"。

### 操作影响链

#### 价格操作
```
降价 → 转化率↑ → 销量↑ → BSR排名↑(变好) → 自然流量↑ → 销量进一步↑(飞轮效应)
     → 但利润率↓ → 需关注长期盈利能力
     → 可能触发竞品跟价 → 价格战风险
     → 幅度匹配检查: 降价10%通常带来20-40%订单增长(视品类弹性)

Lightning Deal → 活动期间销量暴增 → BSR临时飙升 → 活动后回落
              → 可能带来后续自然流量红利(如果排名维持)
              → 可能蚕食日常销量(cannibalization)
              → 幅度匹配检查: LD通常带来3-10倍日销量
```

#### Listing优化
```
标题优化(加词) → 亚马逊重新索引(3-7天) → 新关键词排名 → 搜索流量↑ → 销量↑
              → 但标题过长/堆砌 → CTR↓ → 可能被算法降权
              → 需平衡关键词覆盖与可读性
              → 幅度匹配检查: 单次标题优化通常带来5-20%流量变化

主图优化 → CTR↑(立即生效) → 更多点击 → 更多转化 → 销量↑ → BSR↑
        → 但主图不合规 → 可能被亚马逊下架 → 灾难性影响
        → 幅度匹配检查: 主图优化通常带来10-30% CTR变化
        → 注意: 首图影响远大于副图

Bullet Point优化 → 关键词索引+转化率提升 → 销量↑(延迟7-14天)
                 → 影响相对温和，不如标题和主图显著
                 → 幅度匹配检查: 通常带来<10%变化
```

#### 评论/评分
```
差评涌入 → 评分↓ → 转化率↓(1-2周后) → 销量↓ → BSR↓
        → 亚马逊可能降低展示权重
        → 需紧急处理(测评/客服跟进)
        → 幅度匹配检查: 1个1星差评对高评分产品(4.5+)影响<2%，对低评分产品(3.5-4.0)影响可达5-10%

好评增加 → 评分↑ → 转化率↑ → 销量↑ → BSR↑
        → 效果渐进，通常4-8周显现
        → Vine评论通常在注册后7-21天开始涌入
```

## Important Notes / 注意事项

1. **相关性≠因果性**：时间匹配只是必要条件，不是充分条件。必须结合三轴评分和因果逻辑判断。
2. **幅度匹配是被忽视的关键检查**：minor操作不应导致critical级变化。当幅度不匹配时，即使时间方向都对，置信度也必须降级。
3. **季节性是最大混淆因素**：必须检查类目季节性表，旺季期间的自然增长不能简单归因于运营操作。
4. **混淆因素自动降级**：窗口内存在混淆因素时，置信度自动降一级。
5. **多事件竞争不强行选一**：报告所有候选事件，标注低置信度。
6. **观察期要足够**：标题/Bullet Point变更需至少观察14天，评论变化需30天。
7. **BSR排名方向**：排名数值下降=变好，上升=变差。务必注意Y轴方向。
8. **数据精度限制**：截图中的数据为估算值，分析结论应注明数据来源局限。当数据来自 data-fetch 技能（MCP获取）时，订单量仍为基于BSR的估算值，需标注 `is_estimated=true`。
9. **运营操作间隔建议**：建议运营操作间隔至少7天，便于后续归因区分。
10. **技能联动**：当数据来自 `amazon-monitoring-data-fetch` 技能时，检查 manifest.json 中的数据来源和缺失情况。如关键数据缺失，降级分析并在报告中标注。如用户仅提供ASIN编号，自动回退到 data-fetch 获取数据。
11. **竞品操作还原**：当用户意图为"还原竞品操作/复刻操作"时，重点分析竞品ASIN的 `listing_changes.csv`，按时间线还原操作序列，并结合趋势数据评估每个操作的效果，生成可复刻的操作建议。
