# DTC 店铺运营变更规划

## 目标

把“帮我改店铺”先转成一个安全的静态工作包：

- 当前对象和状态是什么；
- 具体要改什么、为什么；
- 哪些字段归品牌、价格、库存、订单、开发或合规责任方；
- 改之前必须满足哪些条件；
- 会影响哪些页面、渠道、市场和流程；
- 如何回滚；
- 如何验证功能与业务结果；
- 谁审批、谁执行、谁复核。

本 Skill 不读取实时店铺，也不执行变更。

## 开始条件

至少需要：

- 店铺、市场、环境和目标对象；
- 带导出时间和覆盖范围的当前快照；
- 请求的变更与业务理由；
- 期望值、允许范围和生效时间；
- 依赖的品牌、价格、库存、政策或技术决定；
- 执行、审批和验证责任人。

只有需求描述而没有当前快照时，可以做 discovery 清单，不能形成可执行变更包。

`uploads/` 保持只读；过程材料写入 `temp/brand-marketing/<run-id>/03-dtc-change-plan/`，正式结果写入 `outputs/brand-marketing/<run-id>/03-dtc-change-plan/`。

## 执行流程

### 1. 冻结变更集合

说明：

- 哪个店铺、市场、环境和销售渠道；
- 涉及商品、变体、集合、内容、价格、折扣、库存、结账或配置中的哪些对象；
- 计划何时生效、持续多久；
- 本次明确不包含什么；
- 变更失败的业务后果。

不要把多个无关目标塞进一个 change set。高风险、不同责任方或不同上线窗口的变更应拆分。

### 2. 验证当前快照

检查快照：

- 导出或生成时间；
- 店铺/环境/市场范围；
- 对象标识和变体关系；
- 字段定义、币种和语言；
- 是否完整、截断或已过期；
- 是否与其他快照冲突。

快照只能证明对应时点的状态。冲突时先确认哪个更接近当前真实后台，不选择对计划更方便的版本。

### 3. 识别对象与依赖

对每项变更说明目标对象及关联：

- 产品与变体；
- 市场、价格表和币种；
- 库存地点和可售量；
- 集合、导航、页面和搜索；
- 折扣、自动规则和叠加；
- 订单、税务、配送和支付；
- 内容、图片、SEO 和结构化数据；
- 应用、主题或集成。

对象标识不清或关系冲突时停止该项，不凭标题或相似名称匹配。

### 4. 按领域路由责任

- 产品事实、品牌语言和资产 → 品牌/内容责任方；
- 价格、毛利和优惠边界 → 第14利润专家或定价责任方；
- 库存、履约和仓内可用性 → 第08供应链/仓储责任方；
- 税务、合规和政策 → 第09专家；
- 主题、应用、API 和发布 → 开发者；
- 订单或客户个案 → 对应客服/运营责任方。

本 Skill 只编排，不替各领域创造事实。

### 5. 写清变更前置条件

常见前置条件：

- 当前快照仍有效；
- 对象身份和关系已确认；
- 内容、价格、库存和政策已批准；
- 素材权利和语言版本齐全；
- 依赖应用或主题兼容；
- 执行窗口和人员已安排；
- 回滚值与验证方法可用。

任一关键前置条件不满足时，该项保持阻塞。

### 6. 设计回滚

回滚不只是“改回去”。应明确：

- 需要保存哪些变更前值；
- 哪些对象必须按顺序恢复；
- 哪些操作不可逆或可能产生订单/客户影响；
- 谁有权限决定回滚；
- 触发条件和响应时限；
- 回滚后怎样验证。

内容和配置可以恢复，并不代表订单、支付、邮件或搜索缓存等外部后果一定可逆。

### 7. 设计验证

至少覆盖：

- **字段验证**：目标值是否正确；
- **关系验证**：商品、变体、集合、市场和库存关系是否未破坏；
- **前台验证**：页面、语言、价格、可售状态和导航是否正确；
- **交易验证**：结账、税费、折扣、配送或支付是否按预期；
- **运营验证**：订单、库存和客服流程是否可继续；
- **观测验证**：上线后何时检查，谁判断成功或回滚。

验证应使用可观察结果，不只写“检查无误”。

### 8. 形成人工执行计划

按执行顺序列出：

- 变更前备份与复核；
- 每一步目标、责任人和依赖；
- 应用前后的值；
- 审批门；
- 验证与失败判断；
- 回滚步骤；
- 交接和记录。

计划、已批准、执行中和已验证完成必须区分。本 Skill 生成时所有外部动作均未执行。

## 三 MCP 与外部工具边界

`sif_mcp`、`sellersprite_mcp`、`sorftime_mcp` 的 Amazon、TikTok、1688 或其他公开观察不能证明用户 DTC 店铺后台状态，本 Skill 不调用它们。

也不调用 Shopify AI Toolkit、Storefront/UCP MCP、Sidekick、Admin API、GraphQL/REST、CLI、主题、ESP、支付或物流工具；不读取凭据、不创建商品、不处理订单、不修改任何字段。

## 失败与降级

- 快照过期或范围不明：只交付重新导出清单；
- 对象无法唯一匹配：停止该项，要求人工确认；
- 领域事实未批准：路由责任方，不自行补值；
- 回滚不可行：提高审批级别，拆小变更并设计额外验证；
- 多项变更依赖混乱：拆成有顺序的 change set；
- 用户要求直接执行：明确越界，只交人工计划。

## 质量门

- 目标店铺、环境、市场和对象清楚；
- 当前快照的时间、覆盖和限制已说明；
- 对象未按名称猜测匹配；
- 每个字段由正确责任方批准；
- 变更前置条件、影响面和执行顺序清楚；
- 回滚包含值、顺序、触发和复核；
- 验证覆盖字段、关系、前台、交易和运营；
- 未把计划写成已执行；
- 未连接或修改店铺。
