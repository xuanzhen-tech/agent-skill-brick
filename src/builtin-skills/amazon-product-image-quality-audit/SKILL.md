# Amazon 商品图片质量审计

## 目标与单一责任

把“这张图不好”拆成可定位、可解释、可修复、可复核的问题。每个问题必须回答：

1. 审计的是哪个资产、版本和路径；
2. Agent 是否真的观察到了相关像素内容；
3. 哪个可见区域或元数据构成问题证据；
4. 它可能影响准确性、识别、理解、信任或生产就绪中的哪一项；
5. 应修改什么、保留什么、怎样验收。

责任边界固定如下：

- 本 Skill 拥有独立图片审计、问题账本、返工规格和修订验收；
- Product 内置 `amazon-product-image-generation` 单一拥有实际生成、编辑、批量终态管理、资产版本和版本链；
- 内置 Skill 的生成时质量门不替代本 Skill 对任意现有资产的独立审计；
- 专家 03 拥有 A+ 模块、顺序和文案；本 Skill 只核对视觉资产是否忠实服务上游模块任务、资产要求和事实来源。

本 Skill 不直接调用图像生成或编辑工具。用户要求修改时，先交付精准问题账本，再把受影响资产交给内置 Skill。

## 运行合同

### 合法输入

- 用户提供或只读 `uploads/` 中可实际访问的 PNG、JPEG、WebP、PDF 页面或图片集合；
- 可信上游 `outputs/` 中的图像 artifact、资产清单、版本信息、产品事实、视觉 brief 和 A+ 需求；
- 用户提供的当前品牌规则、运营规则与审计目标。

图片来源、权利和版本必须独立记录。文件名相同不代表版本相同，能够读取元数据不代表已经观察像素。

### 外部数据与三 MCP 边界

- 本包不直接调用 `sif_mcp`、`sellersprite_mcp`、`sorftime_mcp`；公开 Listing/A+/视频/评论或 TikTok benchmark 必须先由本地化/研究 Skill 固化为可追溯上游，TikTok 只在用户明确的 TikTok 任务中允许；
- 上游 MCP 证据须保留供应商与精确工具、原始结果位置、平台/站点/ASIN/变体/资产/期间、实际覆盖及压缩/截断限制；本包读取时保留上游文件与版本；
- 供应商观察只能作为 brief/benchmark，不能证明图片像素、实体产品外观、品牌授权、权利、合规或发布资格；材料性同类证据仅在口径可比时并列，不盲目平均或隐藏冲突；
- 产品事实只能来自用户材料或带来源定位的可信上游，不用供应商 Listing 观察填补产品真相缺口；
- 不使用网页、浏览器、Amazon 抓取、其他 MCP/API、Gateway/HTTP/shell 或外部图片诊断服务，也不接触凭据。

合法输入足够时继续；事实或观察能力不足则把相应维度写为“未评估”并说明原因，必要时整体失败关闭。

### 图片观察与问题依据

每条图片观察绑定冻结资产、版本和具体区域，说明 Agent 实际看到了什么、观察条件与不能判断的内容。每个问题再引用相关观察、产品事实、品牌规则或上游要求，解释影响机制、修复规格、验收方式、优先级与待确认项。

输入材料保留来源路径、版本、权利和上游限制；观察与问题不能覆盖原始证据。像素观察及其影响机制都是 Agent 判断，不得写成 CTR、CVR、排名或下架因果事实。

### 工作区

- `uploads/` 只读；
- `temp/visual-content/<case-id>/02-image-quality-audit/` 存放冻结清单、观察记录、缩略图或局部核对中间产物；
- `outputs/visual-content/<case-id>/02-image-quality-audit/` 存放唯一正式审计。

不得覆盖源图片，不得把临时预览冒充正式资产。

## 启动检查

### 最低输入

至少明确：

1. `case_id`、Amazon 站点、目标语言和审计目标；
2. 每个资产的名称、版本和文件路径；
3. 资产角色、目标槽位和变体范围；
4. 足以核对外观与宣称的产品事实；
5. 已知品牌、权利和当前运营约束；
6. 若来自 A+，上游模块、资产和事实依据。

缺少版本标识时为本次审计记录一个快照名称，并说明它不是生产系统版本号。审计进行中发生变化时，新建版本记录，不覆盖原对象。

### 两个审计业务门

1. 观察门：说明当前 Agent 看到了完整图像、只看到局部/降采样预览、只能读取元数据，还是无法访问。只有实际观察到的范围可以产生视觉问题；仅有元数据或无法访问时，不评估视觉维度，也不凭文件名推断。
2. 事实与权利门：资产版本是否冻结，产品事实是否足够，源资产权利是否确认。事实或版本陈旧、来源冲突时暂停相应判断；权利未确认时可以审计可见质量，但不能认定可生产或可发布。

只能观察部分资产时就交付部分审计并写明范围；无法取得审计对象或关键事实时停止。生成、编辑、法律裁定、发布或效果保证不属于本 Skill。

## 观察能力与输入预检

本包只预检当前 Agent 对本地资产的真实观察能力和输入证据：

1. 冻结资产路径、版本、格式、尺寸和可解码状态；
2. 确认当前能力实际观察到完整图片、局部区域还是仅元数据；
3. 核对产品事实、品牌规则和上游要求是否具有可定位证据；
4. 将观察范围外的维度写为“未评估”并说明原因；
5. 输入冲突、文件不可读或事实不足时停止受影响判断。

不得直接调用三个 MCP 补图片内容，也不得猜媒体内容、产品外观、权利或政策结论。

## 执行流程

### 第一步：冻结审计对象

读取 `references/image-audit-observation-and-evidence-contract.md`，为每个资产记录：

- 资产名称、版本、文件路径、文件指纹或本次快照标识；
- 资产角色、槽位、市场、语言和变体；
- 观察状态、观察范围、观察时间和使用能力；
- 上游模块、资产和事实依据；
- 来源与权利状态。

审计报告标题、问题账本和返工交接必须引用同一冻结标识。

### 第二步：建立保留清单

先记录不应被返工破坏的有效部分：

- 正确的产品形态、颜色、材质、部件和比例；
- 清楚的资产角色与主体识别；
- 已证且准确的文字、单位和标识；
- 权利清楚的品牌元素；
- 与资产套图一致的光照、背景和构图语言。

审计不是无差别重做。

### 第三步：逐维度观察

仅在观察与证据支持时检查：

- 产品身份：外观、变体、包装和部件是否符合事实；
- 事实宣称：可见文字、图标和场景是否超出已核实事实；
- 资产职责：主图、卖点图、场景图或 A+ 资产是否完成指定任务；
- 缩略识别：缩略尺度下主体与关键信息是否仍可识别；
- 信息层级：信息顺序、文字负担、对比和移动端可读性；
- 场景可信度：动作、比例、环境和使用方式是否真实；
- 跨资产一致性：产品、变体、Logo、包装与视觉系统是否一致；
- 来源与权利：资产来源与使用范围是否可追溯；
- 用户提供的当前规则：只核对适用于当前站点和期间的规则。

没有相应能力、事实或当前规则时，写明该维度未评估或需运营方核验。

### 第四步：建立逐问题记录

每个问题独立记录：

- 精确资产名称、版本、路径和区域；
- 可见观察与对应事实；
- 问题类型和直接依据；
- 直接依据的 Observation 与输入证据；
- Agent 对影响机制的解释；
- 不能证明的效果与待确认项；
- 影响机制与受影响资产；
- 必须保留内容；
- 精准修复动作；
- 修改后验收；
- 优先级、状态与不确定性。

不要把多个不同根因压成“图片不专业”或“转化差”一句话。

### 第五步：安排优先级

不使用总分、固定权重或字母等级。优先级只使用：

- 必须修复：事实错误、产品/变体错配、权利阻断或会误导用户；
- 高价值修复：证据充分，修复可明显改善识别、理解或资产职责；
- 细节优化：局部表达、对齐或一致性改进；
- 需要补证：疑似问题，但缺少决定性事实或规则；
- 未评估：范围、观察能力或证据不支持。

优先级不代表效果预测。

### 第六步：形成局部返工规格

用户要求修改时，只交接受影响资产：

- 精确资产名称、版本、路径和问题区域；
- 必须保持、允许改变、禁止新增；
- 可使用源资产与权利范围；
- 修复动作、直接依据和验收；
- 未受影响资产继续冻结。

将交接传给内置 `amazon-product-image-generation`。本 Skill 不直接编辑，也不指定外部模型、服务、重试或存储实现。

### 第七步：执行修订验收

返工结果必须创建新版本，不能覆盖原审计对象。逐项复核：

1. 原问题是否解决；
2. 保留清单是否完整；
3. 是否引入新事实、权利或一致性问题；
4. 跨资产身份锚点是否仍成立。

无法观察新版本时，明确写“新版本不可观察”，不能关闭问题。

### 第八步：写入正式交付

使用 `assets/templates/image-quality-audit-delivery-template.md`，分别物化主报告、问题 CSV 和证据账本。

## 失败与沟通

- 资产未冻结：先固定资产、版本和路径，不开展审计；
- 资产不可观察：视觉维度不评估，只报告元数据或访问问题；
- 产品事实缺失：停止事实一致性判断；
- 权利未知：可以指出质量问题，但不能写“可直接发布”；
- 平台规则待确认：列出当前运营方需核验的问题，不做合规保证；
- 来源冲突：列出冲突证据和影响，暂停受影响判断；
- 外部背景不受支持：拒绝用 MCP、网页或其他外部观察填补图片、产品事实、权利或政策缺口；
- 超出范围：生成、编辑、上传、法律裁定或效果承诺。

失败不会触发三个 MCP、网页、其他外部来源或诊断服务回退。

## 正式交付

数据就绪时至少生成：

1. `image-quality-audit.md`：对象、观察范围、保留项、问题、优先级和返工交接；
2. `image-issue-ledger.csv`：一行一个可复核问题；
3. `image-audit-evidence-ledger.md`：输入证据、Observation、Issue 判断、直接依据、限制和权利。

无法观察图片时只生成 `data-readiness.md` 或明确的 metadata-only 报告，不得生成视觉问题。最终回复只链接 `outputs/` 正式文件。

## 质量门

- 每个资产冻结了名称、版本和文件路径；
- 每个视觉结论绑定具体观察和真实观察范围；
- 不可观察维度明确写为“未评估”，没有按零分处理；
- 每个问题包含证据、影响机制、修复、保留项和验收；
- 输入材料、图片观察与问题判断之间可追溯；
- 权利状态与政策待核验项没有被写成通过；
- 没有评分、权重、字母等级、CTR/CVR、排名或下架保证；
- 返工只解冻受影响资产，编辑与版本链交给内置 Skill；
- 正式文件在 `outputs/`，中间文件在 `temp/`，源资产未改变。

## 资源读取

- 冻结资产和建立问题记录前读取 `references/image-audit-observation-and-evidence-contract.md`。
- 写正式审计前读取并物化 `assets/templates/image-quality-audit-delivery-template.md`。
