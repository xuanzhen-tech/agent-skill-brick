# Amazon 账号运营风险控制

## 目标

把“怎样降低账号操作风险”转成一套能落地、能复核的治理方案：

- 主体、受益所有人、账号、品牌和服务商关系真实透明；
- 每个人只拥有完成职责所需的访问；
- 注册、银行、税务、地址、联系人和商品材料与真实情况一致；
- 敏感变更经过审批、执行留痕和事后验证；
- 离职、外包、设备丢失和凭据风险有明确处置；
- 每项整改有负责人、期限和有效性验证。

完成评估不代表 Amazon 已批准业务安排，也不保证账号不会被审核、限制或关联。

## 安全硬边界

遇到下列目标必须拒绝，不提供工具、参数、采购建议或“仅供研究”的步骤：

- 反检测或“防关联”浏览器；
- Canvas/WebGL/字体/时区/语言/硬件等指纹伪装；
- Cookie、local storage、token 或 session 搬运、注入、复用或隐藏；
- 住宅、移动、轮换代理或地理位置伪装；
- MAC、磁盘、设备 ID、系统序列号或虚拟机身份改造；
- 身份、受益所有人、地址、电话、银行、税务或 KYC 材料伪造；
- 壳公司、借名主体、买卖/租借账号或账号农场；
- 绕过封禁、审核、二次验证、平台权限或限制；
- 隐瞒共同控制、共同受益所有人或真实运营关系；
- 反向推断或测试 Amazon 风控算法。

拒绝后只提供合法替代：真实披露、平台确认、法律或税务意见、账号整合、最小权限、材料纠正、事件响应和人工申诉准备。

## 合法多实体前提

多实体或多账号只有在以下条件下进入治理：

- 有真实、可证明的业务理由；
- 主体、受益所有人和控制关系如实记录；
- 第09专家、Amazon 书面说明或合格专业人员确认政策适用性；
- 需要时完成平台披露或事前批准；
- 目标是职责、权限、材料和审计治理，而非隐藏关联。

缺少政策或批准时，暂停高风险结构变化，不写“平台允许”。

## 输入与工作区

使用用户对话、只读 `uploads/` 或可信 `outputs/` 中的：

- 主体结构、账号与站点清单、品牌和业务职责；
- 人员、角色、授权、设备、远程访问和服务商清单；
- 注册、银行、税务、地址、联系人、品牌授权和商品合规材料；
- 敏感变更、离职撤权、事故和整改记录；
- 第09专家带日期、站点、范围和限制的政策判断。

不接收或读取密码、验证码、私钥、Cookie、session、OAuth/LWA 凭据或恢复码。

`uploads/` 保持只读；过程材料写入 `temp/account-risk/<case-id>/04-operational-control/`，正式结果写入 `outputs/account-risk/<case-id>/04-operational-control/`。身份、账号、联系方式、证件、银行、税号、设备和网络信息只保留掩码或材料定位。

## 执行流程

### 1. 筛查真实意图

先问用户希望解决的业务问题。若目标是隐藏关系或绕过限制，拒绝违规部分；若同时存在合法治理需求，可以继续完成合法范围，并明确两者边界。

不要为了证明拒绝理由而复述可操作细节。

### 2. 绘制真实关系图

按“经营主体—受益所有人—账号/站点—品牌—运营团队—服务商”梳理关系。每条关系说明：

- 真实业务理由和生效时间；
- 谁拥有、控制、授权或提供服务；
- 依据是公司材料、合同、平台记录还是用户说明；
- 是否需要披露、批准或专业复核；
- 有什么冲突或尚未核验之处。

相似地址、姓名、设备或网络不够支撑同一控制关系；来源冲突时并列，不自动合并身份。

### 3. 评估人员和服务商访问

逐人核对：

- 工作职责与所需角色是否一致；
- 当前权限是否超出职责；
- MFA、获批设备和远程访问是否有证据；
- 授权、复核、到期和撤销日期是否明确；
- 高权限是否有期限和审批；
- 离职、转岗或合同结束是否及时撤权；
- 紧急访问是否有批准、到期和事后复盘。

多人共享个人凭据、永久管理员权限、服务商无到期访问都是高优先级问题。

### 4. 检查职责分离

关注同一人是否能独立完成高风险闭环，例如：

- 创建、批准并执行银行或税务变更；
- 修改账号主体资料同时批准变更；
- 发布 Listing 同时跳过合规复核；
- 新增管理员同时审核自己的权限；
- 创建退款或付款并自行批准。

若团队规模很小无法完全分离职责，设计补偿控制：双人见证、事后独立复核、限时授权、异常报告和定期抽查。

### 5. 检查设备与会话安全

只设计保护真实身份与账号的合法控制：

- 公司或用户授权的托管设备；
- 系统和浏览器安全更新、磁盘加密、屏幕锁和恶意软件防护；
- 获批的企业远程访问；
- 丢失设备撤权和会话注销流程；
- MFA 恢复责任与安全托管；
- 下载和共享空间最小化；
- 访问日志留存与人工复核。

不得把“制造不同环境”或改变设备指纹作为控制。

### 6. 核对关键材料一致性

逐类比较真实信息与各系统/文件记录：

- 法定名称、注册号、受益所有人；
- 营业、运营和退货地址；
- 电话、邮箱和联系人；
- 银行账户与收款主体；
- 税务、VAT/EPR、海关信息；
- 商标、品牌授权和供应链文件；
- 商品安全、认证与 Listing 陈述。

发现差异时说明当前值、真实值、业务解释、生效时间、影响范围、需要谁判断和如何纠正。合法且有材料支持的差异不等于风险规避；也不得为了“看起来不关联”制造差异。

### 7. 审查敏感变更

主体、受益所有人、银行、税务、地址、联系人、管理员、服务商、品牌授权、合规材料、关键设备与业务结构变更，都应做到：

1. 写明业务原因和变更前后；
2. 完成政策、法律、税务或安全复核；
3. 由适当责任人批准；
4. 安排执行窗口和负责人；
5. 保留验证材料；
6. 准备失败处置或回滚方案；
7. 变更后独立复核。

本 Skill 只设计和评估，不执行变更。建议不能写成已完成。

### 8. 治理服务商

核验服务商真实身份、合同范围、数据边界、允许访问的账号和功能、分包商、跨境数据处理、授权到期与撤权。禁止服务商收集个人账号密码。

若发现共享凭据、越权访问或可疑规避请求，立即升级给账号负责人和安全责任方。

### 9. 处理事件

未授权访问、权限未撤销、材料冲突、误改账号资料、凭据泄露、可疑服务商行为或平台通知发生时：

1. 保护材料并重建时间线；
2. 由授权人员执行平台与身份安全处置；
3. 明确受影响账号、人员、设备和资料；
4. 平台执法原因转 `amazon-account-enforcement-root-cause-analysis`；
5. 政策/IP问题转第09专家；
6. 记录纠正、预防和有效性验证。

凭据已经暴露时，不读取、不复制；请用户由授权人员通过安全渠道轮换。

### 10. 排定整改路线图

按“立即收敛高风险访问—修复真实材料冲突—完善敏感变更审批—建立周期复核”的顺序排优先级。每项控制说明：

- 风险和当前依据；
- 控制目标与具体设计；
- 负责人、依赖和期限；
- 当前真实进度；
- 怎样验证完成并验证有效；
- 实施后仍剩余什么风险。

“已计划”“执行中”“用户称完成”和“有证据验证完成”必须区分。

## 三 MCP 与执行边界

`sif_mcp`、`sellersprite_mcp`、`sorftime_mcp` 的公开商品、流量、销量、广告、Review、商标或市场数据不能证明主体、KYC、访问身份、设备、权限、平台允许性或控制执行，本 Skill 不调用它们。

也不调用 Seller Central、SP-API、浏览器、远程桌面、设备管理、网络或代理工具；不登录、不扫描、不监控、不自动告警或阻断。

## 失败与降级

- 关系不完整：展示已知关系和冲突，列最小补证，不判断允许性；
- 缺政策或批准：暂停多账号或高风险结构建议；
- 权限清单不完整：不声称最小权限已经实现；
- 服务商访问未核验：写“尚未核验”，不能写“无第三方访问”；
- 事故材料不足：不推断攻击者或 Amazon 内部结论；
- 用户要求持续监控：提供人工检查清单和未来接入条件；
- 用户要求预测算法：拒绝；
- 只剩公开市场数据：失败关闭，不补造账号事实。

## 质量门

- 已先完成意图筛查；
- 多实体有真实理由、关系和披露/批准判断；
- 未把隐藏痕迹当作目标；
- 权限符合最小权限、MFA、到期和撤销；
- 职责冲突有分离或补偿控制；
- 设备措施是安全治理而非指纹伪装；
- 材料差异围绕真实事实；
- 敏感变更有审批、证据和复核；
- 服务商访问有合同边界和撤权；
- 未记录凭据、Cookie、session 或恢复码；
- 不预测算法，不保证账号不会受限；
- 每项关系、差距和建议都说明直接依据及未核验项；
- `uploads/` 未改动，敏感信息已掩码。
