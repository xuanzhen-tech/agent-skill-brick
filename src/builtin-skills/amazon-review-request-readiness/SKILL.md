# Amazon Review 请求就绪核对

## 只回答一个问题

基于当前合法材料，这笔订单是否已经具备交给授权人员进一步人工执行的条件？

合格核对必须：

- 锁定单笔订单、站点、观察时点和责任人；
- 核对订单、履约/送达、既有请求、敏感案件和当前政策；
- 按当前政策计算时间窗口，不用记忆中的固定天数；
- 禁止激励、评价引导和按预计好评筛选；
- 明确结论是 `human_execution_ready` 或 `blocked`；
- 始终说明请求尚未执行。

就绪只代表材料通过本 Skill 的人工前置检查，不代表已发送、平台已接受或买家会评价。

## 开始条件

要判断为可交人工继续，至少需要：

1. 掩码订单标识与 marketplace；
2. 可定位订单记录；
3. 当前政策要求的履约或送达时间及其时区；
4. 当前、适站点且可定位的 Review 请求政策；
5. 既有请求历史及其覆盖范围；
6. 当前退货、退款、A-to-z、拒付、安全或其他敏感案件情况；
7. 人工审核人和观察截止时间。

任一关键政策或订单事实缺失时，结论必须是阻塞，并告诉用户缺什么、为什么影响判断。

## 工作区与隐私

`uploads/` 保持只读。过程材料写入 `temp/customer-experience/<case-id>/03-review-request/`，正式结果写入 `outputs/customer-experience/<case-id>/03-review-request/`。

不保存完整买家姓名、地址、邮箱、电话或支付信息，不建立“高分倾向”买家名单。

## 执行流程

### 1. 锁定单笔订单

确认站点、订单、商品、观察截止时间、时区、人工审核人以及本次是首次核对还是复核。不同订单不能合并为一个结论；批量任务也要逐笔过同一门槛。

### 2. 核对订单与履约材料

整理订单创建、付款、发货、政策要求的配送或送达时间，以及取消、退货、退款、A-to-z、拒付、安全和客服案件。

每份导出说明导出时间、筛选范围、时区和覆盖限制。没有看到请求记录不等于从未请求，只有覆盖范围足够完整且明确无记录时才可采用。

### 3. 核对当前政策

政策依据至少应清楚：

- 对哪个 marketplace 和订单类型适用；
- 原文位置及发布/更新或核验时间；
- 资格条件；
- 时间窗口的锚点、起止规则和边界是否包含；
- 重复请求要求；
- 排除项和未决问题。

不得依赖训练记忆、历史模板、博客或“行业惯例”。政策过期、站点不明或来源冲突时，阻塞并交第09专家补证。

### 4. 计算政策窗口

严格按政策原文：

1. 识别窗口锚点；
2. 从订单/履约材料读取对应时间；
3. 保留原时区并说明换算；
4. 判断起止边界是否包含；
5. 展示计算过程和观察时点；
6. 临界边界交人工复核。

缺送达或其他锚点时不能用下单日、发货日或估计时间替代。

### 5. 检查重复请求

说明请求历史覆盖什么时间、如何匹配订单、记录了哪种请求、状态是什么意思以及是否存在延迟。

有可信材料表明已经请求时，直接阻塞。历史记录不完整或相互冲突时，也阻塞，而不是“可以再试一次”。

### 6. 检查敏感案件和政策排除

根据当前材料和政策核对：

- 活跃退货或退款争议；
- A-to-z、拒付、法律或安全案件；
- 政策明确排除的订单状态或对象；
- 与买家的高风险问题是否仍未解决。

存在敏感案件时交授权人员处理。不要根据买家情绪、订单金额或预测评分决定是否请求。

### 7. 执行反操纵门

出现以下任一做法必须阻塞：

- 用优惠券、退款、赠品、补偿或利益换取 Review；
- 要求、暗示或引导正面/五星 Review；
- 把帮助、保修或退款与先评价绑定；
- 只选择预计满意、已留好评或高价值买家；
- 排除可能差评买家以美化评分；
- 混淆 Review、Feedback、商品问答或客服满意度；
- 要求直接发送、排程或绕过平台标准流程。

### 8. 给出就绪结论

只有以下全部满足，才写 `human_execution_ready`：

- 单笔订单材料完整且无关键冲突；
- 当前政策可定位并适用于该站点；
- 窗口计算可复核；
- 既有请求情况明确；
- 无已识别敏感案件或政策排除；
- 无激励、选择性或评价引导；
- 人工责任人明确。

否则写 `blocked`，并以业务语言列出所有原因，如“缺当前政策”“缺送达锚点”“已请求”“不在已确认窗口”“存在敏感案件”“记录冲突”或“请求方式违规”。

### 9. 生成人工证据包

只交付：

- 订单与时间材料摘要；
- 政策原文定位和窗口计算；
- 重复请求核对；
- 敏感案件与排除项核对；
- 就绪/阻塞结论；
- 人工执行前检查表。

不生成个性化 Review 索取话术，不创建发送文件、计划任务或自动化。

## 三 MCP 与外部工具边界

三个市场研究 MCP 没有订单、买家、送达、请求历史或资格后台语义，本 Skill 不调用它们。SellerSprite 与 Sorftime 的公开 Review/VOC 不能证明订单身份、送达状态、请求资格、既有请求或政策窗口。

也不调用 Amazon SP-API、Request a Review、Seller Central、邮件、消息、浏览器或飞书；不读取凭据，不发送、排程、批量触发或模拟请求。

## 失败与降级

- 缺当前政策：阻塞并说明需要第09专家或用户提供什么；
- 缺订单或送达锚点：阻塞，不估算；
- 请求历史不完整：阻塞，不推断未请求；
- 政策或记录冲突：并列材料，交责任方裁决；
- 存在激励、引导、选择性请求或直接发送要求：阻塞并说明合规原因；
- 外部工具不可用：保持阻塞，不换 Web 或其他来源。

## 正式交付

使用 `assets/templates/review-request-readiness-template.md` 生成：

1. `review-request-readiness.md`
2. `review-request-evidence-ledger.md`
3. `policy-window-calculation.csv`（存在窗口计算时）

材料严重不足时可只生成 `data-readiness.md`，但仍要明确结论为 `blocked` 及业务原因。

## 质量门

- 只判断单笔订单；
- 当前政策而非固定天数决定窗口；
- 窗口锚点、时区和边界可复核；
- 未把没有记录误写成零次请求；
- 未把公开 Review 当订单资格材料；
- 未按好评概率、满意度或买家价值筛选；
- 未产生激励、评价引导或私下联系话术；
- 明确尚未发送、排程或执行；
- PII 已最小化；
- 每个阻塞理由有直接材料或清楚的缺口说明。
